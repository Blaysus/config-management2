# Практическая работа № 2. Вариант 22. Этапы 1 и 2

CLI-приложение на Python для анализа зависимостей пакетов Alpine Linux.
На втором этапе программа читает настройки из TOML, скачивает индекс
`APKINDEX.tar.gz`, находит пакет по точным имени и версии и выводит
его прямые зависимости. Для чтения HTTP, gzip и tar используется только
стандартная библиотека Python. Менеджеры пакетов и сторонние библиотеки
получения зависимостей не используются.

Первый этап сохранен в истории отдельным коммитом. Его демонстрация
доступна через `--show-config`. Построение графа с DFS, ограничение
глубины обхода, обратные зависимости и PlantUML относятся к этапам 3–5.

Репозиторий: https://github.com/Blaysus/config-management2.

## Требования и запуск

Нужен **Python 3.11 или новее**. Модуль `tomllib` входит в стандартную
библиотеку. Сборка проекта и установка пакетов через pip не требуются.
Все команды ниже выполняются из корня репозитория.

Второй этап, реальный репозиторий Alpine:

```sh
python3 -m src.main
```

Другой пакет или конфигурационный файл:

```sh
python3 -m src.main --config examples/curl.toml
python3 -m src.main --config examples/musl.toml
```

Пример без сети с локальным текстовым APKINDEX:

```sh
python3 -m src.main --config examples/test_config.toml
```

Первый этап: проверить и вывести все пять настроек без сетевого запроса:

```sh
python3 -m src.main --show-config
```

Скрипт для macOS и Linux и справка:

```sh
./run.sh --config examples/config.toml
./run.sh --show-config
python3 -m src.main --help
```

Скрипт также запускается через `sh run.sh`. Интерпретатор можно выбрать
командой `PYTHON=python3.11 ./run.sh`. В Windows используйте
`py -3 -m src.main`. Относительный путь в `--config` отсчитывается от
текущего каталога терминала; `run.sh` работает и из другого каталога.

## Настройки TOML

Все пять ключей обязательны и задаются на верхнем уровне, без секций.
Неизвестные ключи отклоняются. `--config` выбирает файл, а
`--show-config` выбирает режим вывода; значения параметров берутся из TOML.

| Ключ | Тип и проверка | Назначение |
| --- | --- | --- |
| `package_name` | Непустая строка: латинские буквы, цифры, `.`, `_`, `+`, `-`; первый символ - буква или цифра. | Точное имя пакета. |
| `repository` | HTTP(S)-URL с узлом и корректным портом или читаемый обычный файл при `test_mode = true`. | Каталог архитектуры репозитория, готовый URL `APKINDEX.tar.gz` или локальный текстовый APKINDEX. |
| `test_mode` | Только логическое `true` или `false`, без кавычек. | Выбор локального файла вместо HTTP. |
| `package_version` | Непустая строка, начинающаяся с цифры; далее допустимы латинские буквы, цифры, `.`, `_`, `+`, `~`, `-`. | Точная версия, включая ревизию `-rN`. |
| `max_depth` | Целое число не меньше `0`; строки, дроби и логические значения запрещены. | Настройка для обхода графа на этапе 3. На этапе 2 проверяется, но не ограничивает список прямых зависимостей. |

Относительный путь локального индекса отсчитывается от каталога
TOML-файла. Абсолютные пути и `~` поддерживаются. В режиме вывода
настроек сохраняется исходный путь из конфигурации.

Индекс скачивается из указанного каталога архитектуры: например,
`https://dl-cdn.alpinelinux.org/alpine/v3.20/main/x86_64`.
Название `APKINDEX.tar.gz` добавляется автоматически. Также можно
указать полный URL этого файла. Query-параметры URL сохраняются.
Для формата APK v2 читаются поля `P` (имя), `V` (версия), `D` (зависимости).

## Поведение второго этапа

Выбирается только точная пара имя-версия. Если версия отсутствует,
выводится ошибка со списком доступных версий; другая версия автоматически
не подставляется. Доступность версии проверяется в выбранном репозитории
и архитектуре, а не во всех репозиториях Alpine.

Зависимости выводятся как требования из поля `D`: ограничения версий,
`so:` и `cmd:` сохраняются. Например, `so:libz.so.1` обозначает требование
к библиотеке; поиск пакета-поставщика на этом этапе не выполняется.
Поля `p` (предоставляемые возможности) и `i` (условия установки)
не добавляются в список прямых зависимостей. Элементы `!имя` из поля `D`
сохраняются отдельно как конфликты и не выводятся как зависимости.
Пакет без поля `D` имеет пустой список зависимостей.

Архив обрабатывается в памяти, файлы на диск не извлекаются. Читаются
также составные gzip/tar с подписью Alpine. Криптографическая проверка
подписи индекса не реализована. Проверка HTTPS-сертификата выполняется
стандартными средствами Python.
Таймаут запроса - 20 секунд; ограничения объема: ответ HTTP - 16 МиБ,
распакованный tar - 64 МиБ, текст APKINDEX - 32 МиБ.

## Демонстрационные примеры

`examples/config.toml`:

```toml
package_name = "zlib"
repository = "https://dl-cdn.alpinelinux.org/alpine/v3.20/main/x86_64"
test_mode = false
package_version = "1.3.2-r0"
max_depth = 3
```

Ожидаемый результат:

```text
Прямые зависимости zlib (1.3.2-r0):
so:libc.musl-x86_64.so.1
```

Для `examples/curl.toml`:

```text
Прямые зависимости curl (8.14.1-r2):
libcurl=8.14.1-r2
so:libc.musl-x86_64.so.1
so:libcurl.so.4
so:libz.so.1
```

Для `examples/musl.toml`:

```text
Прямые зависимости musl (1.2.5-r4):
Прямых зависимостей нет.
```

Эти версии проверены по реальному индексу 1 ноября 2026 года.
Содержимое удаленного репозитория со временем обновляется; при удалении
версии программа сообщит об этом и перечислит доступные.

Локальный пример использует `examples/test_config.toml` и
`examples/test_repository.txt`. Файл репозитория содержит записи APKINDEX:

```text
P:A
V:1.0-r0
D:B C

P:B
V:1.0-r0
D:D
```

В полном примере также есть пакеты C и D. Результат:

```text
Прямые зависимости A (1.0-r0):
B
C
```

D не выводится: он является транзитивной зависимостью. Для пакета A
здесь задана глубина `0`; на втором этапе выводятся его прямые зависимости.
Формат локального файла на этом этапе - текстовый APKINDEX,
с полями версии, как у удаленного индекса. Чтение отдельного описания
графа вида `A: B C` относится к третьему этапу.

## Ошибки и их демонстрация

Ошибки направляются в `stderr`, частичный результат не выводится.
Код завершения при ошибке - `2`, при успехе - `0`.

Ошибки всех пяти параметров первого этапа:

```sh
python3 -m src.main --config examples/errors/package_name.toml
python3 -m src.main --config examples/errors/repository.toml
python3 -m src.main --config examples/errors/test_mode.toml
python3 -m src.main --config examples/errors/package_version.toml
python3 -m src.main --config examples/errors/max_depth.toml
```

Демонстрация отсутствующей версии на втором этапе:

```sh
python3 -m src.main --config examples/errors/version_not_found.toml
```

Дополнительно обрабатываются отсутствие конфигурации и локального файла,
ошибки UTF-8 и TOML, лишние и пропущенные ключи, ошибки HTTP и соединения,
таймаут, обрыв ответа, превышение лимитов, поврежденный gzip/tar,
отсутствие APKINDEX в архиве, ссылка вместо обычного файла, повторные
индексы, поля или пары имя-версия, неверные P/V и отсутствующий пакет.
Некорректные индексы не маскируются под пакеты без зависимостей.

## Тесты по этапам

Расположение тестов заданием не фиксируется. Они разделены по этапам,
чтобы первый этап можно было проверить отдельно от получения зависимостей.

```sh
python3 -m unittest discover -s tests -p 'test_stage1.py' -v
python3 -m unittest discover -s tests -p 'test_stage2.py' -v
```

Весь набор:

```sh
python3 -m unittest discover -s tests -v
```

`test_stage1.py` содержит 30 проверок параметров, чтения TOML и CLI
с `--show-config`. `test_stage2.py` содержит 32 проверки разбора APKINDEX, точной
версии, прямых зависимостей, обоих источников, архивов, ошибок и вывода CLI.
Всего проходят 62 теста.
HTTP в тестах заменен управляемыми ответами; внешняя сеть не требуется.
Архивы создаются в памяти и не попадают в репозиторий.

Функции конфигурации в `src/config.py`:

| Элемент | Назначение |
| --- | --- |
| `Config`, `ConfigError` | Проверенные настройки и ошибка конфигурации. |
| `load_config(path)` | Чтение TOML, обработка ошибок файла и запуск проверки. |
| `parse_config(data, base_dir)` | Проверка словаря настроек и создание `Config`. |
| `_validate_fields(data)` | Проверка обязательных и неизвестных ключей. |
| `_require_text(value, name)` | Проверка непустой строки без управляющих символов. |
| `_validate_package_name(value)` | Проверка формата имени. |
| `_validate_package_version(value)` | Проверка текстового формата версии. |
| `_validate_repository(value, test_mode, base_dir)` | Выбор проверки URL или локального файла. |
| `_validate_url(value)` | Проверка схемы, узла и порта URL без обращения к сети. |
| `_validate_test_file(value, base_dir)` | Проверка доступности локального файла. |
| `_validate_max_depth(value)` | Проверка целой неотрицательной глубины. |

Функции разбора в `src/apk_index.py`:

| Элемент | Назначение |
| --- | --- |
| `Package`, `RepositoryError` | Данные пакета и ошибка получения данных. |
| `_parse_fields(record)` | Чтение P, V и D из одной записи. |
| `_make_package(fields)` | Проверка P/V, разделение зависимостей и конфликтов. |
| `parse_index(text)` | Разбор записей и проверка уникальности пар имя-версия. |
| `find_package(packages, name, version)` | Поиск точной версии с понятной ошибкой. |

Функции получения данных в `src/repository.py`:

| Функция | Назначение |
| --- | --- |
| `build_index_url(repository)` | Построение URL APKINDEX.tar.gz. |
| `_read_limited(source, limit)` | Чтение потока с ограничением размера. |
| `download_index(repository)` | HTTP-запрос с таймаутом и обработкой ошибок. |
| `_decode_index(data)` | Строгое декодирование UTF-8. |
| `_read_archive_member(archive)` | Чтение единственного обычного APKINDEX из tar. |
| `extract_index(data)` | Обработка gzip/tar и составных архивов. |
| `read_test_index(repository, base_dir)` | Чтение локального текстового APKINDEX. |
| `get_package(config, base_dir)` | Выбор источника, разбор и поиск версии. |

Функции CLI в `src/main.py`:

| Функция | Назначение |
| --- | --- |
| `create_parser()` | Справка, `--config` и `--show-config`. |
| `print_config(config)` | Пять строк в формате ключ-значение. |
| `print_dependencies(package)` | Вывод прямых зависимостей или сообщения об их отсутствии. |
| `main(argv=None)` | Выполнение выбранного режима и код завершения. |

Назначение каждого теста описано его docstring. Вспомогательные функции
`make_tar`, `make_archive` создают данные в памяти, а `run_main`
перехватывает результат CLI для проверки.

## Требования оформления и коммит второго этапа

Проверяются исходники и тесты: файлы до 1000 строк, строки Python до
80 символов, функции до 40 строк, до 7 аргументов, цикломатическая
сложность до 10. У модулей, классов и функций есть docstring; числовые
сравнения используют именованные константы, имена соответствуют PEP 8.
`setUp` является стандартным переопределением `unittest.TestCase`.

Фактические максимумы после проверки: строка Python - 80 символов,
функция - 18 строк, аргументов - 3, сложность - 8.

В корне есть README, .gitignore, src, tests и run.sh. Кэш Python, архивы,
результаты сборки и настройки редакторов исключены через .gitignore.
В репозитории хранятся только текстовые файлы проекта.

После проверки тестов второй этап сохраняется новым коммитом, без
изменения коммита первого этапа:

```sh
git add -A -- README.md src tests examples
git diff --cached --check
git diff --cached --stat
git commit \
  -m "feat(deps): implement variant 22 stage 2" \
  -m "Fetch and parse Alpine APKINDEX using the Python standard library." \
  -m "Select the exact version, print direct dependencies and handle errors." \
  -m "Separate tests by stage and update examples and documentation."
git push origin main
```

Технический источник формата P/V/D и синтаксиса зависимостей:
[исходный код Alpine apk-tools](https://github.com/alpinelinux/apk-tools/blob/v2.14.4/src/package.c).
